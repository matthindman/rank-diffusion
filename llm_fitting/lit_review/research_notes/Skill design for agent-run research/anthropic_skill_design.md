Retrieved 2026-10-11. Every source was fetched directly by URL; no web search was used. Scope: what Anthropic's own documentation, engineering posts, the Agent Skills open specification and the `anthropics/skills` skill-creator say about skill and instruction-file design, and what changes for Opus 5.x / Fable 5.x.

How to read these notes:

- **Findings are close paraphrases, not quotations.** To stay inside quotation limits I reproduce only one verbatim sentence fragment in the whole file (marked as such, in section 3). Where exact wording matters, the section heading of the source page is given in italics as a locator so the wording can be pulled directly. Numbers, field names, commands and setting names are reproduced exactly.
- **"Cited findings" are what a source says; "Inferences" are mine.** Inferences about the rank-diffusion skills rest on a read-only profile of the four `SKILL.md` files (sizes, headings, word counts), not on a full reading of them.
- **Model generation matters.** The general prompting page mixes statements measured on different models and itself says that a technique naming a specific model should be treated as measured on that model and re-checked against your own evals before being applied to another ([PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), *General principles*). ## 1. Skill anatomy and mechanics today

### Takeaway
A skill is a folder whose `SKILL.md` has two required frontmatter fields (`name`, `description`) and a body that loads only when the description matches the task; scripts and reference files load or run only when the body points to them. The sources converge on a short navigational body (under 500 lines, about 5k tokens), references one level deep, facts needed in every session in a short CLAUDE.md, and anything that must hold every time in hooks or permissions rather than in either file.

### Cited Findings

Frontmatter and limits
- Required: `name` (1–64 chars, lowercase letters, digits and hyphens, no leading, trailing or doubled hyphen, must equal the directory name) and `description` (1–1024 chars, says what the skill does and when to use it, includes task keywords). Optional: `license`, `compatibility` (max 500 chars), `metadata` (string map), `allowed-tools` (experimental). — [SPEC](https://agentskills.io/specification)
- Anthropic's platform adds: no XML tags in either field, and `name` may not contain the reserved words "anthropic" or "claude". — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [OV](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)
- Claude Code accepts further optional fields: `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context` (`fork`), `agent`, `background`, `hooks`, `paths`, `shell`. Unrecognised fields are ignored without an error. Outside Claude Code (claude.ai uploads, Skills API) only the specification fields are accepted. — [CCS](https://code.claude.com/docs/en/skills) (via summariser)
- In Claude Code the combined `description` + `when_to_use` text is cut at 1,536 characters per skill in the listing, so the key use case goes first. The whole listing has a budget of 1% of the context window; on overflow, descriptions of the least-invoked skills are dropped first. — [CCS](https://code.claude.com/docs/en/skills), *Skill descriptions are cut short*

How descriptions drive triggering
- Name and description are preloaded into the system prompt (about 100 tokens per skill); the description is what Claude matches the request against. — [OV](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview), *Level 1: Metadata*
- Write the description in third person, be specific, include key terms, and state both capability and trigger contexts; Claude may be choosing among 100+ skills. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Writing effective descriptions*
- agentskills.io instead advises imperative phrasing addressed to the agent, a focus on user intent rather than internals, listing contexts where the skill applies even when the user does not name the domain, and brevity. — [ASOD](https://agentskills.io/skill-creation/optimizing-descriptions), *Writing effective descriptions*; partly contradicts the third-person rule in [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- skill-creator says Claude currently tends to under-trigger skills and asks authors to make descriptions somewhat assertive, with all when-to-use information in the description rather than the body. — [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *Write the SKILL.md*
- Agents consult a skill only when the task needs something beyond what they can do unaided; a simple one-step request may not trigger even a perfectly matching description. — [ASOD](https://agentskills.io/skill-creation/optimizing-descriptions), *How skill triggering works*; [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *How skill triggering works*
- Vague or overlapping descriptions lead to the wrong skill loading or a useful one being missed. — [FO](https://code.claude.com/docs/en/features-overview), *Understand how features load*
- If a skill fires too often, make the description more specific or set `disable-model-invocation: true`. — [CCS](https://code.claude.com/docs/en/skills), *Skill triggers too often*

Progressive disclosure and body size
- Three stages: metadata always; `SKILL.md` body when triggered (under 5k tokens); bundled files when referenced (no cost until read; scripts cost only their output). — [OV](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview), *How Skills work*; [SPEC](https://agentskills.io/specification), *Progressive disclosure*
- Keep the body under 500 lines and split when approaching that. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Progressive disclosure patterns*; [CCS](https://code.claude.com/docs/en/skills); [SPEC](https://agentskills.io/specification)
- Keep references one level deep from `SKILL.md`: Claude may only preview a file reached through a chain of references and so act on partial information. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Avoid deeply nested references*
- Give reference files a table of contents: over 100 lines per [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (*Structure longer reference files with table of contents*); over 300 lines per [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md) (*Progressive Disclosure*). The two thresholds differ.
- Say when each reference file should be loaded (a condition, not a generic pointer). — [ASBP](https://agentskills.io/skill-creation/best-practices), *Structure large skills with progressive disclosure*
- Organise references by domain with descriptive filenames so only the relevant file is read. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Pattern 2: Domain-specific organization*

Scripts versus prose
- Instructions suit flexible guidance, code suits reliability, resources suit factual lookup. — [OV](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview), *Level 3: Resources and code*
- Pre-made scripts are more reliable than generated code, save tokens and time, and give consistency; state whether a script is to be executed or read as reference. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Provide utility scripts*
- If test transcripts show every run re-inventing the same helper, bundle it as a script. — [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *How to think about improvements*; [ASBP](https://agentskills.io/skill-creation/best-practices), *Bundling reusable scripts*

Lifecycle inside a Claude Code session
- An invoked skill's rendered body enters the conversation as one message and stays; the file is not re-read on later turns, so guidance meant for the whole task must be written as standing instruction rather than a one-off step. — [CCS](https://code.claude.com/docs/en/skills), *Claude stops following a skill*
- After compaction Claude Code re-attaches the latest invocation of each skill, keeping the first 5,000 tokens of each within a shared 25,000-token budget; the docs therefore say to put the most important instructions near the top and to re-invoke the skill to restore the full text. — [CCS](https://code.claude.com/docs/en/skills), *Claude stops following a skill*; [CW](https://code.claude.com/docs/en/context-window)
- The skill listing itself is not re-injected after `/compact`; only invoked skills are preserved. — [CW](https://code.claude.com/docs/en/context-window)
- Hooks declared in a skill's `hooks` frontmatter apply from invocation until the session ends. — [CCS](https://code.claude.com/docs/en/skills), *Claude stops following a skill*
- `` !`command` `` placeholders run before Claude sees the skill and are replaced by the command's output; a failing command aborts the invocation. `paths` globs restrict automatic activation to matching files. `context: fork` runs the skill as a subagent task. — [CCS](https://code.claude.com/docs/en/skills) (via summariser)
- `disable-model-invocation: true` keeps the description out of context and is recommended for workflows with side effects that should only run when the user names them. — [CCBP](https://code.claude.com/docs/en/best-practices), *Create skills*; [FO](https://code.claude.com/docs/en/features-overview), *Understand how features load*

Every-session content versus some-task content
- CLAUDE.md loads in full every session; skills cost only their descriptions until used; hooks cost nothing unless they return output. — [FO](https://code.claude.com/docs/en/features-overview), *Context cost by feature*
- CLAUDE.md is for facts needed in every session (build commands, conventions, layout, always-do rules); a multi-step procedure or something relevant to one part of the codebase belongs in a skill or a path-scoped rule. — [MEM](https://code.claude.com/docs/en/memory), *When to add to CLAUDE.md*
- Target under 200 lines per CLAUDE.md; longer files reduce adherence; `@` imports organise but do not reduce context cost. — [MEM](https://code.claude.com/docs/en/memory), *Write effective instructions*
- `.claude/rules/*.md` with `paths` frontmatter load only when Claude reads or edits matching files. — [MEM](https://code.claude.com/docs/en/memory), *Path-specific rules*
- CLAUDE.md is delivered as a user message after the system prompt and is treated as context, with no guarantee of strict compliance; to block an action use a `PreToolUse` hook. — [MEM](https://code.claude.com/docs/en/memory), *Claude isn't following my CLAUDE.md*
- By default Claude Code reads `AGENTS.md` only when no `CLAUDE.md` or `CLAUDE.local.md` exists on the path; a CLAUDE.md can import it with `@AGENTS.md`; nothing under a `.agents/` directory is read as instructions. A CLAUDE.md that merely tells Claude in words to read another file is seen only if Claude decides to open that file. — [MEM](https://code.claude.com/docs/en/memory), *AGENTS.md*
- Subagents start with their own system prompt, the CLAUDE.md hierarchy (except the built-in Explore and Plan agents, or agents with `omitClaudeMd`), and the full text of skills named in their `skills` field; the main conversation's auto memory is not loaded. — [SUB](https://code.claude.com/docs/en/sub-agents) (via summariser); [FO](https://code.claude.com/docs/en/features-overview)
- Plugins are the packaging layer for skills, hooks, subagents and MCP servers; custom skills do not sync between claude.ai, the API and Claude Code. — [FO](https://code.claude.com/docs/en/features-overview); [OV](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview), *Cross-surface availability*

### Inferences
- The core `stochastic-modeling/SKILL.md` is 407 lines, so it passes the 500-line guide, but at about 28 KB / 3,905 words (my estimate: 6–8k tokens, not measured) it exceeds the ~5k-token body guidance and the 5,000-token post-compaction re-attachment cap. In a long session the sections that sit last (pitfall catalogue, current state, handoff hygiene) are the ones that would silently drop out after compaction.
- "Must be read every session" cannot be delivered by a skill (description-triggered, model's choice) or by a CLAUDE.md sentence telling Claude to open a file. What actually loads every session is root CLAUDE.md, unscoped rules and `@` imports (at full context cost); what actually enforces is hooks and permissions.
- The third-person rule (BP) and the imperative rule (ASOD) are reconciled by the pattern both sources use in their examples: one third-person capability sentence followed by a "Use when ..." clause.
- For a skill mirrored to `.agents/skills/` for other agents, the shared `SKILL.md` should carry only specification-level frontmatter; Claude Code-specific fields are either ignored or rejected elsewhere, so Claude Code enforcement is better placed in `.claude/settings.json` than in skill frontmatter.

### Gaps
- The middle of the Claude Code skills page (frontmatter reference, lifecycle) was read through a summariser; field semantics should be re-checked against the page before relying on a specific field.
- I did not research how Codex or other agents treat unknown frontmatter or `.agents/skills/`.

## 2. Writing guidance

### Takeaway
Write only what the model does not already know, match prescriptiveness to how fragile each step is, explain the reason behind a constraint instead of shouting it, and keep volatile material out. Checklists, validators and plan-validate-execute are the recommended devices for steps that must not be skipped.

### Cited Findings

Conciseness
- Assume the model is already very capable; add only context it lacks and challenge each paragraph's token cost. The page's good and bad examples differ by a factor of three in length for the same instruction. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Concise is key*
- Test for each item: would the agent get this wrong without it? If not, cut; if unsure, test. If the agent already does the whole task well without the skill, the skill may add nothing. — [ASBP](https://agentskills.io/skill-creation/best-practices), *Add what the agent lacks, omit what it knows*
- Overly comprehensive skills can hurt: the agent struggles to find what is relevant and may follow instructions that do not apply. Concise stepwise guidance with a working example tends to beat exhaustive documentation. — [ASBP](https://agentskills.io/skill-creation/best-practices), *Aim for moderate detail*
- For CLAUDE.md: for each line ask whether removing it would cause mistakes; bloated files cause real instructions to be ignored. — [CCBP](https://code.claude.com/docs/en/best-practices), *Write an effective CLAUDE.md*

Degrees of freedom
- High freedom (prose) when several approaches are valid and decisions depend on context; medium (pseudocode or parameterised scripts) when a preferred pattern exists; low (a specific script, few or no parameters) when operations are fragile, consistency is critical or a sequence must be followed. The page's analogy is a narrow bridge versus an open field. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Set appropriate degrees of freedom*
- Most skills mix both; calibrate each part separately. — [ASBP](https://agentskills.io/skill-creation/best-practices), *Match specificity to fragility*
- Teach a reusable approach to a class of problems rather than the answer to one instance. — [ASBP](https://agentskills.io/skill-creation/best-practices), *Favor procedures over declarations*
- Give one default with an escape hatch rather than a menu of options. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Avoid offering too many options*

Reasons instead of emphatic imperatives
- Giving the motivation behind an instruction helps Claude generalise; the page's example replaces a bare capitalised prohibition with a sentence explaining the downstream consequence. — [PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), *Add context to improve performance*
- skill-creator: explain why things matter rather than relying on heavy-handed capitalised commands; finding yourself writing all-caps ALWAYS or NEVER is a warning sign to reframe with reasoning. — [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *Writing Style* and *How to think about improvements*
- Reason-bearing instructions work better than rigid directives because models follow more reliably when they know the purpose. — [ASEV](https://agentskills.io/skill-creation/evaluating-skills), *Iterating on the skill*
- State what to do rather than what not to do. — [PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), *Control the format of responses*
- Counter-current: BP's iteration example lists stronger wording as one possible fix when a tester instance misses a rule, alongside reorganising for prominence. CCBP says that if Claude keeps skipping one instruction, add emphasis to that line alone, because emphasising many lines makes none stand out. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Develop Skills iteratively with Claude*; [CCBP](https://code.claude.com/docs/en/best-practices), *Write an effective CLAUDE.md*

Examples, templates, workflows, checklists
- Examples steer format and style more reliably than description; three to five diverse, relevant examples are suggested. — [PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), *Use examples effectively*; [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Examples pattern*
- Prefer a curated set of canonical examples over a long list of edge cases. — [CE](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Templates: strict wording for formats that must be exact, flexible wording where adaptation helps. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Template pattern*
- Break complex operations into sequential steps; for particularly complex ones provide a checklist the model copies and ticks off, which keeps validation steps from being skipped. BP's own first example is a research-synthesis checklist with a citation-verification step that loops back on failure. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Use workflows for complex tasks*
- Large workflows can be pushed into separate files selected by task type. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Conditional workflow pattern*
- A gotchas list of environment-specific facts that defy reasonable assumptions is often the highest-value content; keep it in `SKILL.md`, where it is read before the situation arises, and add to it whenever a correction is needed. — [ASBP](https://agentskills.io/skill-creation/best-practices), *Gotchas sections*

Feedback loops and plan-validate-execute
- Run validator, fix, repeat; the validator can be a script or a reference document the model checks against; only proceed when validation passes. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Implement feedback loops*
- Plan-validate-execute: write the plan in a structured file, validate it with a script against a source of truth, then execute; recommended for batch, destructive and high-stakes operations. Validators should emit specific, corrective error messages. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Create verifiable intermediate outputs*; [ASBP](https://agentskills.io/skill-creation/best-practices), *Plan-validate-execute*
- Scripts should handle error cases themselves and document every constant rather than leave the model to work it out. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Solve, don't defer*

Terminology, time-sensitive content, old patterns
- Pick one term per concept and use it throughout. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Use consistent terminology*
- Do not include information that will go out of date; put superseded material in a collapsed "old patterns" section so it gives history without cluttering the main content. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Avoid time-sensitive information*
- CLAUDE.md's exclude list includes information that changes frequently, anything derivable from the code, long explanations, and file-by-file descriptions. — [CCBP](https://code.claude.com/docs/en/best-practices), *Write an effective CLAUDE.md*

Altitude
- Aim between two failure modes: brittle hard-coded logic and vague guidance that assumes shared context. Seek the minimal set of information that fully specifies the behaviour (minimal is not necessarily short); start minimal on the best model and add instructions in response to observed failures. — [CE](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- The research-system team reports that its prompting aims to instil good heuristics rather than rigid rules, modelled on how skilled human researchers work, with explicit guardrails against runaway behaviour. — [MA](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- The profile of the four skills shows rule pressure coming less from capitals than from density: `stochastic-modeling` has 25 case-insensitive "never", 6 "binding", a "non-negotiable" section heading and 64 bold spans, but only two literal all-caps NEVER. The rewrite target is the count of unexplained prohibitions and the bolding, not just the capitals.
- Only `python -m pytest` appears as an executable command in the core skill; almost every safeguard is prose. By the degrees-of-freedom rule, the narrow-bridge steps are under-scripted and the open-field parts are over-constrained.
- The pitfall catalogue is the kind of content the sources rate highest (gotchas), so the question is which entries a Claude 5 model still gets wrong, not whether to keep the genre.

## 3. What changes for stronger models

### Takeaway
Guidance written specifically for the Claude 5 family exists and is explicit: skills written for earlier models tend to be too prescriptive and can lower output quality, a short instruction now does the work of an enumerated list, and verification, status and thinking scaffolds carried over from older prompts should be removed or re-tested. What is still asked for is purpose, explicit scope and boundaries, evidence-backed progress claims, a memory location, and executable checks.

## 4. Evaluation-driven skill development

### Takeaway
Anthropic's stated order is evaluations first, then the minimum instructions that pass them, with a no-skill or old-skill baseline run in clean contexts beside each with-skill run, transcripts read as well as outputs, and a held-out split when tuning descriptions.

### Cited Findings
- Build evaluations before writing extensive documentation: run the model on representative tasks without the skill and record failures; write three scenarios that test those gaps; measure the baseline; write just enough to pass; iterate. Evaluations are the source of truth. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Build evaluations first*
- Develop with two instances: one helps write and refine the skill, a fresh one uses it on real tasks; bring observed behaviour back as specifics. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Develop Skills iteratively with Claude*
- Watch navigation: unexpected reading order, missed references, over-reliance on one section (promote it to the body), files never opened (remove or signal better). — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Observe how Claude navigates Skills*
- BP's checklist asks for at least three evaluations and tests on each model tier with real usage scenarios. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Checklist for effective Skills*
- skill-creator loop: draft, write 2–3 realistic test prompts, launch with-skill and baseline subagents in the same turn (baseline is no skill for a new skill, a snapshot of the old version when improving one), draft assertions while runs proceed, grade with scripts where possible, aggregate pass rate, time and tokens with mean, standard deviation and delta, have a human review outputs, revise, repeat. — [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *Running and evaluating test cases*
- Revision rules: generalise from feedback rather than patching for the test cases; keep the prompt lean and remove what is not earning its place; read transcripts for wasted effort; explain the why; bundle repeated helper code. — [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *How to think about improvements*
- If pass rates plateau as rules are added, the skill may be over-constrained; try removing instructions and see whether results hold. — [ASEV](https://agentskills.io/skill-creation/evaluating-skills), *Iterating on the skill*
- Each run starts in a clean context; assertions are added after the first outputs are seen; a pass needs concrete evidence; assertions that pass in both arms are uninformative and should be replaced; inconsistent results point to ambiguous instructions; blind comparison of two versions complements assertion grading. — [ASEV](https://agentskills.io/skill-creation/evaluating-skills)
- Description optimisation: about 20 realistic queries (8–10 should trigger, 8–10 near-miss should not), each run 3 times, trigger-rate threshold 0.5, a fixed 60/40 train/validation split, up to about five iterations, select by validation score, then check on 5–10 fresh queries. Avoid adding keywords lifted from failed queries. — [ASOD](https://agentskills.io/skill-creation/optimizing-descriptions); [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *Description Optimization*
- `claude plugin eval` runs a plugin against cases with graders (`regex`, `tool_used`, `tool_order`, `file_exists`, `llm`, `baseline`), 3 runs per case per arm by default, with a no-plugin baseline arm; a `tool_used: Skill` grader measures triggering. It is offered for catching regressions when the plugin changes or a new model is released. For iterating on one skill inside a conversation the docs point to skill-creator's `evals/evals.json` flow instead. — [PE](https://code.claude.com/docs/en/plugin-evals)
- `claude plugin validate .claude/skills` finds `SKILL.md` files whose frontmatter does not parse; `/skill-doctor` helps find skills worth turning off. — [CCS](https://code.claude.com/docs/en/skills), *Skill not triggering* and *Skill descriptions are cut short*
- General eval practice: start with 20–50 tasks drawn from real failures; write tasks two experts would grade the same way, with a reference solution; balance cases where a behaviour should and should not occur; isolate environments; grade outcomes rather than the path taken; run multiple trials and choose between at-least-once and every-time metrics; do not trust a score until transcripts have been read. — [EV](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Research agents: combine groundedness, coverage and source-quality graders, and calibrate rubric judges against expert human judgment. About 20 queries from real usage sufficed early because early changes had large effects. — [EV](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [MA](https://www.anthropic.com/engineering/multi-agent-research-system)
- Keep a held-out test set when optimising against evals. — [WT](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Start from real expertise: synthesise from the project's own incident records, review comments and fixes rather than generic best practice. — [ASBP](https://agentskills.io/skill-creation/best-practices), *Start from real expertise*

## 5. Guardrails versus autonomy for high-stakes, irreversible or integrity-critical steps

### Takeaway
The sources separate guidance from enforcement. Instruction files are advisory; anything that must hold every time goes into hooks, permission rules, sandboxing or a script, and the prose keeps only the reason and a short list of stop-and-ask conditions. Everything else is left open.

### Cited Findings
- Instructions in CLAUDE.md or a skill are a request, not a guarantee; a `PreToolUse` hook that blocks the action is enforcement. If a rule must hold every time, make it a hook. — [FO](https://code.claude.com/docs/en/features-overview), *Compare similar features* (Hook vs Skill)
- Hooks are for actions that must happen every time with zero exceptions; CLAUDE.md is advisory, hooks are deterministic. — [CCBP](https://code.claude.com/docs/en/best-practices), *Set up hooks*
- If Claude skipped a skill rule that must hold every time, move it into a hook (it can live in the skill's `hooks` frontmatter); if it skipped guidance meant to be applied with judgment, reword it to cover the whole task. — [CCS](https://code.claude.com/docs/en/skills), *Claude stops following a skill*
- A prompted rule can fail under pressure, in long sessions, or when a file contains an injected instruction; never-do constraints need a `PreToolUse` hook that exits with code 2, or permissions / managed settings. — [ST](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Hook mechanics: a `PreToolUse` command hook that exits 2 blocks the call and returns the stderr reason to the model; structured output can return `permissionDecision` of `deny` or `ask`; a deny holds even in bypass-permissions mode. The guide includes a worked example blocking edits to protected file patterns. — [HG](https://code.claude.com/docs/en/hooks-guide), *Block edits to protected files*, *Structured JSON output*, *Hooks and permission modes*
- For decisions needing judgment there are `prompt` hooks (one model call returning ok / not ok with a reason) and experimental `agent` hooks (a subagent with tools, e.g. confirming tests pass before a stop is allowed). `Stop` hooks fire whenever the model finishes responding and are overridden after eight consecutive blocks. — [HG](https://code.claude.com/docs/en/hooks-guide), *Prompt-based hooks*, *Agent-based hooks*, *Stop hook hits the block cap*
- Permission rules are enforced by Claude Code, not by the model. Evaluation order is deny, then ask, then allow; an allow rule cannot carve an exception from a deny. File rules use `Edit(path)` and `Read(path)` with gitignore-style patterns; rules for `Write` paths are accepted but never consulted. — [PERM](https://code.claude.com/docs/en/permissions), *Manage permissions* and *Read and Edit*
- Limits: Read / Edit deny rules cover Claude's file tools, recognised file commands in Bash and redirection targets, but not commands that read files without naming them or arbitrary subprocesses; Bash argument patterns are fragile. For enforcement independent of command text use sandboxing, or inspect the command in a `PreToolUse` hook. — [PERM](https://code.claude.com/docs/en/permissions), *Bash* and *Read and Edit*
- Use `disable-model-invocation: true` for workflows with side effects so they run only when the user names them. — [CCBP](https://code.claude.com/docs/en/best-practices), *Create skills*
- Low-freedom scripts for fragile operations, with wording telling the model not to alter the command; plan-validate-execute for destructive or high-stakes operations. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Set appropriate degrees of freedom* and *Create verifiable intermediate outputs*
- Make mistakes hard to commit by changing the interface (the SWE-bench example made relative-path errors impossible by requiring absolute paths). — [BEA](https://www.anthropic.com/engineering/building-effective-agents), Appendix 2
- Stop-and-ask conditions, Claude 5 wording: pause only for a destructive or irreversible action, a real scope change, or input only the user can give; proceed on reversible actions that follow from the request. — [F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5), *Strong instruction following*; [F51](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1), *Finish the whole task*
- Reversibility framing (stated for Opus 4.6): encourage local reversible actions, ask before hard-to-reverse, shared or destructive ones, and do not bypass safety checks as a shortcut around an obstacle. — [PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), *Balancing autonomy and safety*
- When the model is made more autonomous for unattended runs, keep your own confirmation step for risky or irreversible actions. — [O55](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5), *Unattended agentic runs*
- Convert a rule the model already follows without being told into nothing, or into a hook. — [CCBP](https://code.claude.com/docs/en/best-practices), *Avoid common failure patterns*

### Inferences
- The programme's integrity invariants map onto the enforcement layer one by one: owner-gated files (frozen specs, `CONFIRMATION_PROTOCOL.md`) fit `ask` rules or a `PreToolUse` hook returning `ask`; one-shot confirmatory data fits a deny rule plus a Bash-inspecting hook or sandbox restriction, because a Python process reading a parquet file is exactly the subprocess case deny rules miss; "append, never rewrite" for `MODEL_STATUS.md` fits a hook or pre-commit script that rejects any diff with deletions in that file; the legacy guard and test suite fit a single invariant-check script run by a Stop hook or before commit.
- A confirmatory run is a plan-validate-execute case: the pre-registration file is the plan, a script validates it (present, committed, hash recorded, dataset not previously opened) and only then releases the data. That makes the one-shot property a property of the tooling rather than of the model's obedience.
- Once those are enforced, the prose can afford to be short and reason-giving, and the remaining text can open up the non-fragile work.
- Hooks and permission rules live in `.claude/settings.json` and bind only Claude Code. For other agents the same checks must be reachable as plain scripts, git hooks or CI, which argues for writing the checks as repository scripts first and wiring Claude Code hooks to call them.

### Gaps
- No Anthropic source discusses pre-registration, blinded or one-shot datasets, or research-integrity controls specifically; the mapping above is by analogy with protected files and destructive operations.
- I did not read the sandboxing page, so the exact filesystem restrictions available for blocking subprocess reads are unverified.
- The hooks reference (full event schemas) was not opened; `agent` hooks are marked experimental.

## 6. Context engineering for long research sessions

### Takeaway
Keep always-loaded instructions small and stable, retrieve the rest just in time through pointers, and hold volatile state in files the model reads and writes during work. Root CLAUDE.md and invoked skills survive compaction in limited form; conversation-only instructions and unscripted state do not.

### Cited Findings
- Context is a finite resource with diminishing returns; the aim is the smallest set of high-signal tokens that makes the wanted outcome likely. — [CE](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Just-in-time retrieval keeps lightweight identifiers (paths, stored queries, links) in context and loads data at run time; Claude Code is a hybrid, with CLAUDE.md placed up front and search tools for the rest. — [CE](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Three long-horizon techniques: compaction (suits back-and-forth work), structured note-taking outside the window (suits iterative work with milestones), and subagents returning condensed summaries (suits research where parallel exploration pays). — [CE](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Performance degrades as the window fills; clear between unrelated tasks, delegate exploration to subagents, and after two failed corrections restart with a better prompt. — [CCBP](https://code.claude.com/docs/en/best-practices), *Manage your session*
- CLAUDE.md can carry a compaction instruction naming what must survive summarisation. — [CCBP](https://code.claude.com/docs/en/best-practices), *Manage context aggressively*
- After compaction the system prompt, project-root CLAUDE.md, memory and MCP tools reload; up to five recently modified files are re-read; invoked skills are re-injected (capped); nested CLAUDE.md files and path-scoped rules reload on demand; instructions given only in conversation are lost. — [CW](https://code.claude.com/docs/en/context-window); [MEM](https://code.claude.com/docs/en/memory), *Instructions seem lost after /compact*
- A `SessionStart` hook with a `compact` matcher can re-inject critical context after every compaction. — [HG](https://code.claude.com/docs/en/hooks-guide), *Re-inject context after compaction*
- Fable 5.1 follows explicit lists of what a compaction summary must keep: problems and resolutions, options tried or set aside and why, decisions and constraints stated exactly, current status, open items, and hard-to-reconstruct specifics. — [F51](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1), *Tell the model what to preserve in compaction summaries*
- Auto memory: `MEMORY.md` is an index (first 200 lines or 25 KB loaded each session), topic files are read on demand, and Claude skips what the code or CLAUDE.md already records; it is machine-local and not loaded into subagents. — [MEM](https://code.claude.com/docs/en/memory), *Auto memory*
- State conventions: JSON for structured state, free text for progress notes, git as log and checkpoint; a fresh window that rediscovers state from the filesystem can beat compaction. — [PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), *State management best practices*
- Long-running harness: an initial session builds the scaffolding (feature list in JSON with a pass field, progress log, initial commit); later sessions make incremental progress and leave structured updates; each session starts by reading the log, the progress file and the feature list and running a basic end-to-end check. JSON was chosen because the model is less likely to rewrite it inappropriately than Markdown. The author flags scientific research as a possible, untested generalisation. — [EH](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (Opus 4.5)
- Research system: save the plan to external memory, summarise completed phases, and have subagents write outputs to storage and pass back references rather than relaying everything through the lead. — [MA](https://www.anthropic.com/engineering/multi-agent-research-system)
- Skills should not hold information that will go stale; CLAUDE.md should exclude information that changes frequently. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Avoid time-sensitive information*; [CCBP](https://code.claude.com/docs/en/best-practices), *Write an effective CLAUDE.md*
- Block-level HTML comments in CLAUDE.md are stripped before injection, so maintainer notes cost no context. — [MEM](https://code.claude.com/docs/en/memory), *How CLAUDE.md files load*

### Inferences
- The programme already has the right durable store: `MODEL_STATUS.md` is the append-only record and git is the checkpoint. What the sources add is that the skill should point to it and say how to read it, not restate its contents. The core skill's "current state and parked items (as of 2026-07-06)" section and the dated frozen-spec numbers are the time-sensitive content the guidance says to move out.
- A small machine-readable state file (current frozen-spec identifiers, gate results with bands, open owner-gated items) would serve both the model's start-of-session routine and the invariant-check script, and is less likely to be casually rewritten than prose.
- Dynamic injection (`` !`command` ``) could print the newest status headings at skill invocation so the skill never stores them, but it is Claude Code-only and aborts the invocation if the command fails; a start-of-session step that runs a script is the portable equivalent.
- Provenance text now in descriptions ("written by ... on ...") can move to an HTML comment or a changelog file at no context cost.

### Gaps
- No source gives guidance on context management for sessions that include very long-running numerical jobs.
- The compaction-survival details come from text embedded in an interactive page; I did not see a plain-prose table of them.

## 7. Anti-patterns the sources name explicitly

### Takeaway
The named anti-patterns cluster into four groups: too much text, emphasis and rigidity as a substitute for reasons or enforcement, stale or misplaced content, and untested skills.

### Cited Findings
- Explaining what the model already knows; verbose bodies. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Concise is key*
- Offering many options instead of a default. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Avoid offering too many options*
- Deeply nested references; Windows-style paths; vague names and vague descriptions; first- or second-person descriptions; inconsistent terminology; time-sensitive statements; magic constants; scripts that fail and leave the model to cope; assuming packages are installed. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Anti-patterns to avoid* and related sections
- Writing documentation before evaluations, so the skill documents imagined problems. — [BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), *Build evaluations first*
- Generating a skill from general model knowledge with no project-specific input, which yields generic procedures. — [ASBP](https://agentskills.io/skill-creation/best-practices), *Start from real expertise*
- Exhaustive edge-case coverage; skills scoped too narrowly (several must load, risking conflict) or too broadly (hard to trigger precisely); a generic pointer to a references folder with no load condition. — [ASBP](https://agentskills.io/skill-creation/best-practices)
- All-caps ALWAYS / NEVER and rigid structures as a warning sign; narrow fixes fitted to the test cases; oppressive constraint lists. — [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), *How to think about improvements*
- Trigger tests whose negative cases are obviously irrelevant; adding keywords from failed queries to the description. — [ASOD](https://agentskills.io/skill-creation/optimizing-descriptions)
- Assertions that always pass regardless of the skill; passing without concrete evidence. — [ASEV](https://agentskills.io/skill-creation/evaluating-skills)
- The over-specified CLAUDE.md in which rules get lost; emphasising many lines; the kitchen-sink session; correcting repeatedly in a polluted context; trusting plausible output with no check; unscoped investigation. — [CCBP](https://code.claude.com/docs/en/best-practices), *Avoid common failure patterns*
- Using CLAUDE.md for always-do behaviours that should be hooks, for never-do constraints that need enforcement, or for long procedures that should be skills; unscoped rules that apply to few paths; shared files that only grow; many appended and contradictory instructions. — [ST](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Brittle hard-coded logic in prompts, and at the other extreme vague high-level guidance; laundry lists of edge cases. — [CE](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Carry-over scaffolding: forced status messages, verification and double-check instructions (Opus 5), think-carefully lines (Opus 5.5 chat), anti-formatting and hold-findings-to-the-end rules (Fable 5.1), prompts that demand written-out reasoning (Claude 5 family), aggressive use-this-tool language (Opus 4.5 / 4.6), and a visible context countdown (Fable 5). — [O5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5); [O55](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5); [F51](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1); [F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5); [PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Blanket conservatism instructions that the model follows literally, suppressing findings. — [O48](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8), *Code review harnesses*
- A reviewer told to find gaps with no bar, which drives over-engineering. — [CCBP](https://code.claude.com/docs/en/best-practices), *Add an adversarial review step*
- Rigid checks of the exact path an agent took rather than its outcome; shared state between trials. — [EV](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Keeping harness components after a model upgrade without testing whether they are still load-bearing. — [HD](https://www.anthropic.com/engineering/harness-design-long-running-apps)

### Inferences
- Matched against the profile, the July skills show at least five of these: point-in-time state in the body, a description that carries a capitalised must-read command and authorship history instead of trigger terms, safeguards expressed only as prose, a body larger than the token guidance, and no evaluation set.

### Gaps
- I found no source that lists anti-patterns for research or scientific skills as such.

## Implications for redesigning the rank-diffusion skills

Ordered by priority. Each item names the principle it rests on. Items are my recommendations, not statements by the sources.

1. **Build the evaluation set before rewriting anything.** Turn recorded failures (pitfall-catalogue entries, failed or superseded results in `MODEL_STATUS.md`) into 20 or so tasks with checkable outcomes, and run three arms on each model that will use the skills: no skill, the July skills as a snapshot, the redesign. Use several trials per task because head metrics are noisy. Grade outcomes with scripts where possible and read the transcripts. Run `/doctor prompt-audit` on `.claude/skills/` as a first-party first pass. Basis: evaluations first and baseline comparison ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), [ASEV](https://agentskills.io/skill-creation/evaluating-skills)); tasks from real failures, multiple trials, transcript reading ([EV](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)); test with every model ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)); prompt audit ([MEM](https://code.claude.com/docs/en/memory)).

2. **Move integrity-critical rules out of prose and into enforcement.** Write each as a repository script first, then wire it up: an `ask` rule or `PreToolUse` hook on edits to frozen specs and `CONFIRMATION_PROTOCOL.md`; a hook or pre-commit check that rejects deletions in `MODEL_STATUS.md`; a deny rule plus a Bash-inspecting hook or sandbox restriction on one-shot confirmatory data; one invariant-check command (legacy guard plus test suite) gated by a Stop hook or commit hook; a block on research-driven edits under the package trees. Make a confirmatory run a plan-validate-execute step whose validator checks the pre-registration before any data is released. Basis: guidance is advisory and guardrails belong in hooks ([FO](https://code.claude.com/docs/en/features-overview), [CCBP](https://code.claude.com/docs/en/best-practices), [ST](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)); permission order and limits ([PERM](https://code.claude.com/docs/en/permissions)); low-freedom scripts and plan-validate-execute for fragile or high-stakes steps ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)); error-proofing through the interface ([BEA](https://www.anthropic.com/engineering/building-effective-agents)).

3. **Replace the role statement.** Drop the framing that the reader should almost never invent. State the purpose (a pre-registered, externally reviewed programme whose value depends on not contaminating confirmatory evidence), then mark two zones: open work where ambition is wanted (diagnostics, competing hypotheses, proposed model extensions, critique of the programme's own assumptions) and gated work (frozen specifications, the acceptance criterion, confirmatory data, the canonical record). Ask for the ambitious behaviour in so many words. Basis: literal instruction following and the conservatism example ([O48](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8), [O5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)); too-prescriptive legacy skills and starting at the top of the difficulty range ([F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)); give the reason ([F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5), [PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)); state boundaries ([F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)).

4. **Cut the core skill to a navigational body and order it for compaction.** Aim for roughly 5k tokens with the purpose, the two zones, the acceptance criterion and the stop-and-ask list in the first screen, since only the first 5,000 tokens survive compaction. Delete material a Claude 5 model does not need (general statistical method, generic workflow advice) wherever the no-skill arm shows it is already done correctly. Basis: body size and progressive disclosure ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [SPEC](https://agentskills.io/specification)); compaction re-attachment ([CCS](https://code.claude.com/docs/en/skills)); cut what the agent already gets right ([ASBP](https://agentskills.io/skill-creation/best-practices), [CCBP](https://code.claude.com/docs/en/best-practices)).

5. **Move specific sections to reference files, one level deep, each with a stated load condition and a table of contents.** Candidates: the flag glossary; the full pitfall catalogue (keep in the body only the short list of non-obvious gotchas the evals show are still missed, one line each with its reason); the new-platform workflow as a checklist file, or merged into `data-intake`; per-platform frozen specifications. Basis: one-level references and tables of contents ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)); load conditions and gotchas ([ASBP](https://agentskills.io/skill-creation/best-practices)); checklists for multi-step workflows ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

6. **Take point-in-time state out of the skills.** Remove the dated current-state section and dated frozen numbers from `SKILL.md`. Keep the canonical record where it is, add a small machine-readable state file for frozen-spec identifiers, gate results with bands and open owner-gated items, and have the skill say how to read both at session start. Put superseded method in a collapsed old-patterns note only if it prevents a known regression. Basis: no time-sensitive content ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [CCBP](https://code.claude.com/docs/en/best-practices)); structured state files and a start-of-session routine ([PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [EH](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); procedures over declarations ([ASBP](https://agentskills.io/skill-creation/best-practices)).

7. **Rewrite rule language.** For each remaining prohibition, either attach the consequence it prevents in one clause or delete it; phrase as what to do; state scope explicitly where broad application is intended; reduce bolding. Keep a short, plainly worded list of pause conditions (irreversible action, scope change, owner decision). Reserve emphasis for the one or two lines the evals show are still skipped after rewording. Basis: reasons over imperatives ([PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md), [ASEV](https://agentskills.io/skill-creation/evaluating-skills)); brief instructions suffice ([F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)); explicit scope ([O48](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8)); emphasis on one line only ([CCBP](https://code.claude.com/docs/en/best-practices)).

8. **Rewrite the four descriptions.** One third-person capability sentence, then a "Use when ..." clause listing concrete triggers in the user's own vocabulary (fit, calibrate, out-of-sample gate, scorecard, new platform, panel, record a session, move files), including cases where the skill is not named. Put the key use first, stay under 1,024 characters, and remove the capitalised must-read command, authorship and date, and the successor-model list. Then test with about 20 queries per skill including near-misses between the four skills, three runs each, on a held-out split. Basis: description rules ([BP](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [SPEC](https://agentskills.io/specification), [CCS](https://code.claude.com/docs/en/skills)); under-triggering and assertive phrasing ([SC](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)); optimisation loop ([ASOD](https://agentskills.io/skill-creation/optimizing-descriptions)).

9. **Fix how every-session content is delivered.** Keep root `CLAUDE.md` short and limited to invariants that apply in every session, since it is the file that loads and survives compaction; stop relying on a sentence that tells the model to read a skill in full; add a compaction instruction naming what must survive (decisions, pre-registered predictions, current gate status, open owner-gated items). Consider importing `AGENTS.md` so one file serves all agents, and move the package-track rules to a path-scoped rule on the package trees. Basis: what loads when and the 200-line target ([MEM](https://code.claude.com/docs/en/memory), [FO](https://code.claude.com/docs/en/features-overview)); compaction instructions ([CCBP](https://code.claude.com/docs/en/best-practices), [F51](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)); path-scoped rules ([MEM](https://code.claude.com/docs/en/memory)).

10. **Keep verification as executable checks and independent review, and delete re-check prose.** Give the model commands that return pass or fail, require results sections to cite the tool output they rest on, and have a fresh-context reviewer check a results entry against the gate outputs before it is appended to the record, with the reviewer limited to correctness and stated requirements. Remove sentences that merely tell the model to double-check. Basis: checks and evidence ([CCBP](https://code.claude.com/docs/en/best-practices)); evidence-audited progress claims and fresh-context verifiers ([F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)); over-verification from carried-over instructions ([O5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)); separate evaluators ([HD](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

11. **Add what the Claude 5 pages ask for and the July skills lack.** A research-notes or hypothesis file convention (competing hypotheses, confidence, self-critique); a lessons directory with one lesson per file; delegation guidance saying when subagents are warranted and what a brief must contain, with a custom subagent that preloads the core skill for delegated modelling work; effort set through configuration and tested on the evals rather than through think-harder prose. Check the skills contain no instruction to write out reasoning verbatim (a quick pattern search found none). Basis: research prompting ([PBP](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)); memory system and delegation ([F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5), [MA](https://www.anthropic.com/engineering/multi-agent-research-system), [SUB](https://code.claude.com/docs/en/sub-agents)); effort calibration ([O55](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5), [F51](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)); reasoning-extraction refusals ([F5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)).

12. **Keep the shared `SKILL.md` portable and treat the skills as code.** Use only specification frontmatter in the mirrored files and put Claude Code-specific enforcement in settings. Re-run the eval set whenever a skill or the model changes, remove one component at a time to see what is still load-bearing, and prune on each model upgrade. Basis: specification fields versus Claude Code fields ([SPEC](https://agentskills.io/specification), [CCS](https://code.claude.com/docs/en/skills)); stale scaffolding and one-at-a-time removal ([HD](https://www.anthropic.com/engineering/harness-design-long-running-apps)); review and prune like code ([CCBP](https://code.claude.com/docs/en/best-practices)); evals speed model adoption ([EV](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

Caveats on this list: items 2, 6 and 9 depend on Claude Code features that other agents do not share; the research-integrity mapping in item 2 is by analogy, since no source discusses pre-registration or one-shot data; and the claim in item 3 that the role statement suppresses useful work is an inference to be confirmed in the three-arm evaluation, not something a source measured for this repository.
