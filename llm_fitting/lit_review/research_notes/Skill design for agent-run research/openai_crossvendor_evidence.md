## Key question 1 — OpenAI Codex: AGENTS.md, skills, prompts, hooks/rules/approvals, subagents, and the AGENTS.md-versus-skills division of labour

### Takeaway
Codex reads `AGENTS.md` on every run (root-to-working-directory concatenation, 32 KiB default cap) and reads Agent-Skills-format `SKILL.md` folders from `.agents/skills` (repo), `~/.agents/skills` (user) and `/etc/codex/skills` (admin), loading only name and description until a skill is selected. OpenAI's stated split is: a small `AGENTS.md` for rules that must hold every session, skills for repeatable procedures, and hooks, rules, sandbox and CI for anything that must actually be enforced.

### Cited Findings
**Where the docs live**
- The `developers.openai.com/codex/...` URLs now permanently redirect (HTTP 308) to `learn.chatgpt.com/docs/...`; the documentation covers "ChatGPT & Codex" as one product family. — [AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [docs index](https://learn.chatgpt.com/llms.txt)

**AGENTS.md**
- Global scope: Codex looks in `~/.codex` (or `CODEX_HOME`) for `AGENTS.override.md`, else `AGENTS.md`, and uses only the first non-empty one. — [AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Project scope: from the project root (normally the Git root) down to the current directory, each directory contributes at most one file, checked in the order `AGENTS.override.md`, `AGENTS.md`, then any names in `project_doc_fallback_filenames`. Discovery stops at the current directory. — [AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Files are concatenated root-downward; guidance nearer the working directory wins because it comes later in the combined prompt. The chain is built once per run (once per launched session in the TUI). — [AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Size cap: `project_doc_max_bytes` defaults to 32 KiB; Codex stops adding files once the combined size reaches it. The suggested remedies are raising the cap or splitting guidance across nested directories. — [AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Verifying what loaded: run `codex --ask-for-approval never "Summarize the current instructions."`, or inspect the TUI/session logs; there is no cache, so a restart picks up changes. — [AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- In the Codex harness each discovered `AGENTS.md` is injected as its own user-role message ahead of the user prompt, in root-to-leaf order. — [Codex Prompting Guide, OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide) (written for `gpt-5.3-codex`, not GPT-6)
- Recommended content: working agreements such as test and lint commands, package-manager preference, asking before adding dependencies; nested files for service-specific rules; concise code-review rules, with formatting and lint left to CI. — [AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- The best-practices guide says a short, accurate file is worth more than a long one full of vague rules; start small, add a rule only after seeing a repeated mistake, and if the file grows, keep the main file concise and point to task-specific Markdown files. — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)

**Skills**
- Codex skills build on the Agent Skills open standard. A skill is a directory with a `SKILL.md` that must contain `name` and `description`; the page documents no other frontmatter fields. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- Scan locations: `$CWD/.agents/skills` and `.agents/skills` in every parent up to the repository root; `$HOME/.agents/skills`; `/etc/codex/skills`; and skills bundled with Codex. The current page does not mention `~/.codex/skills`. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- Two skills with the same name are not merged and both can appear in selectors; no precedence order is given. Symlinked skill folders are supported and followed. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- Triggering is explicit (`/skills` or `$skill-name` in the CLI and IDE extension, `@` in ChatGPT) or implicit, when the task matches the description. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- Progressive disclosure: only name, description and file path are loaded at start; that listing is capped at 2% of the context window, or 8,000 characters when the window size is unknown; with many skills Codex shortens descriptions first and may omit skills with a warning. The full `SKILL.md` loads only on selection; `scripts/`, `references/` and `assets/` are optional. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- Codex-specific settings live in a sidecar file, `agents/openai.yaml`, not in frontmatter: `interface.*` (display name, short description, icons, brand colour, default prompt), `policy.allow_implicit_invocation` (default `true`; when `false` only explicit `$skill` invocation works), and `dependencies.tools` (for example an MCP server). — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- Skills are disabled per path with `[[skills.config]]` (`path`, `enabled = false`) in `~/.codex/config.toml`. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- Authoring advice: one job per skill; prefer instructions to scripts unless determinism or external tooling is needed; write imperative steps with explicit inputs and outputs; test prompts against the description to confirm triggering. — [Build skills](https://learn.chatgpt.com/docs/build-skills)
- OpenAI's own bundled `openai-docs` skill uses `name`, `description` and `metadata.short-description`; its body is roughly 40–50 lines, routes to eight reference files each with an explicit load condition, tells the agent to read at most one primary reference, and uses no ALL CAPS or MUST wording. — [openai/codex `openai-docs/SKILL.md`](https://raw.githubusercontent.com/openai/codex/main/codex-rs/skills/src/assets/samples/openai-docs/SKILL.md)
- The `openai/skills` catalogue repository exists (about 28k stars) but is marked deprecated in favour of the OpenAI Plugins repository; it links to agentskills.io. — [openai/skills](https://github.com/openai/skills)
- Plugins are the distribution unit and skills the authoring format. — [Skills & Plugins](https://learn.chatgpt.com/docs/skills-and-plugins.md), [Customization overview](https://learn.chatgpt.com/docs/customization/overview.md)

**Custom prompts**
- Custom prompts are deprecated in favour of skills. They lived in `~/.codex/prompts/`, were invoked from the slash menu, and could not be shared through a repository. — [Custom Prompts](https://learn.chatgpt.com/docs/custom-prompts.md)

**Hooks, rules, approvals**
- Hooks are configured in `hooks.json` or `[hooks]` tables in `config.toml`, at user level (`~/.codex/`) and repo level (`<repo>/.codex/`); project-local hooks load only when the project is trusted. Events: SessionStart, SessionEnd, PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, UserPromptSubmit, SubagentStart, SubagentStop, Stop, Interrupt. PreToolUse can deny or rewrite a tool call or add model-visible context; a Stop hook can make Codex continue. Hooks are enabled by default, and the page cautions that tool hooks are a guardrail and not a complete enforcement boundary. — [Hooks](https://learn.chatgpt.com/docs/hooks.md)
- Rules (labelled experimental) are Starlark `.rules` files built from `prefix_rule()` calls with a decision of `allow`, `prompt` or `forbidden`; they govern commands run outside the sandbox, live in a `rules/` folder beside each config layer (`~/.codex/rules/default.rules`; `<repo>/.codex/rules/` when trusted), and the most restrictive match wins. — [Rules](https://learn.chatgpt.com/docs/agent-configuration/rules.md)
- Approval policies are `on-request` (interactive default), `never`, and `granular`; `untrusted` has been retired and can stop the client starting. Sandbox modes are `read-only`, `workspace-write` and `danger-full-access`. The recommended default for version-controlled folders is workspace-write with on-request approvals; network access is off by default; the local sandbox is OS-enforced. — [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security.md)

**Subagents and long-running work**
- Local Codex clients spawn subagents only after a direct request or an applicable project or skill instruction; only the "Ultra" level in ChatGPT Work delegates proactively. — [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)
- Custom agents are TOML files in `~/.codex/agents/` or `.codex/agents/` with required `name`, `description`, `developer_instructions` and optional `model`, `model_reasoning_effort`, `sandbox_mode`. Concurrency is capped by `agents.max_concurrent_threads_per_session`. Subagents inherit the sandbox policy and cost more tokens than a single-agent run. — [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)
- Parallel agents are recommended for read-heavy work (exploration, tests, triage, summarisation); the page warns that agents editing at the same time can conflict. — [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)
- Long-running work is started with `/goal` (the goal text doubles as completion criteria) after `/plan` if the outcome is unclear; goals should state the outcome, constraints and verifiable completion checks; a goal does not widen permissions. The page advises against two chats changing the same files and recommends Git worktrees for parallel coding chats. — [Long-running work](https://learn.chatgpt.com/docs/long-running-work.md)
- For longer work the best-practices guide suggests a `PLANS.md` or execution-plan template, `/review` for checking changes, and one chat per coherent unit of work. Its list of common mistakes includes overloading the prompt with durable rules and running live tasks on the same files without worktrees. — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)

**Division of labour**
- `AGENTS.md` holds persistent guidance that applies before work starts and should stay small (build and test commands, review expectations, repo conventions, directory-specific rules); skills hold repeatable procedures that need examples, references or helper scripts; the overview recommends pairing `AGENTS.md` with infrastructure such as pre-commit hooks and linters that enforces its rules. — [Customization overview](https://learn.chatgpt.com/docs/customization/overview.md)
- Suggested adoption order: `AGENTS.md` plus enforcement tooling; then a plugin or a skill; then MCP for external systems; then subagents. — [Customization overview](https://learn.chatgpt.com/docs/customization/overview.md)
- A repeatedly reused prompt is the signal to make a skill; team skills go in `.agents/skills` in the repo and personal ones in `$HOME/.agents/skills`. — [Codex best practices](https://learn.chatgpt.com/guides/best-practices)

### Inferences
- Codex cannot see `.claude/skills/`. The repository's `.agents/skills/` copy is the only thing Codex reads, so any drift between the two trees is invisible to one vendor's agent.
- Because `AGENTS.md` is injected into every Codex run and a skill only on selection, anything that must hold in every session (the acceptance gate, the protected-results rule, the location of the canonical record, owner-gated items) belongs in `AGENTS.md`; procedures belong in skills.
- A skill description that orders the agent to read the whole skill before every session is doing `AGENTS.md`'s job through the trigger channel. Codex provides cleaner mechanisms: an `AGENTS.md` line naming when to load which skill, or explicit `$skill` invocation.
- OpenAI's own bundled skill is an example of the intended shape: a short router with conditional references and plain wording.

### Gaps
- No Codex page states a precedence rule between `AGENTS.md` and skill content. The only precedence statement found is the GPT-6 guide's suggested prompt line putting user instructions above skill guidance (next section).
- The subagents page does not say whether subagents receive `AGENTS.md`.
- How Codex treats unknown frontmatter keys (for example Claude Code extensions) is not documented on the pages read.
- The skills page describes scan directories for "Codex"; whether the ChatGPT desktop app scans a local repository's `.agents/skills` identically is implied by the shared documentation but not stated outright.
- Pages carry no last-updated dates and the changelog was not read, so feature introduction dates are unknown.

## Key question 2 — OpenAI prompting guidance for its newest reasoning and agentic models

### Takeaway
The newest generation is officially named GPT-6, with GPT-6 Astra as flagship, so the owner's phrase matches a real product, and model-specific guidance exists. Its most relevant statement for this project is that Astra reacts more strongly to instructions found in skills and project files, and OpenAI recommends auditing them; the explicit doctrine of simplifying first, measuring, and adding back only the minimum is in the preceding GPT-5.6 guide, not the GPT-6 one.

### Cited Findings
**What the newest generation is called**
- The models page lists GPT-6 Astra (`gpt-6-astra`, top tier, $10/$50 per million tokens), GPT-6.1 Sol (`gpt-6.1-sol`) and GPT-6 Luna (`gpt-6-luna`), all with a 1.05M-token context window and 128K maximum output; Astra's knowledge cutoff is 30 April 2026. No release dates are given. — [OpenAI models](https://developers.openai.com/api/docs/models)

**GPT-6 guide ("Using GPT-6")**
- The one verbatim quotation in these notes: the guide says Astra "can be more sensitive to instructions contained in skills and other files", and strongly recommends auditing every skill and file the model can reach (it names `AGENTS.md`) for instructions that could steer behaviour. — [Using GPT-6: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md)
- Conflicting guidance inside a skill can make the model pause early. The suggested remedies are a prompt line stating that user instructions outrank skill guidelines, and asking the model to name and link the exact `SKILL.md` and instruction that caused a pause. — [Using GPT-6: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md)
- Astra asks for clarification more readily than earlier models, which tended to assume. The suggested prompts tell it to act on requests, proceed autonomously on reversible and read-only work, seek approval only after preparing a reviewable result, and still stop for clearly destructive or irreversible actions. — [Using GPT-6: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md)
- Astra tests thoroughly before declaring completion; the suggested prompt discourages tests that merely mirror a small reversible change and says to widen or repeat testing only when new changes or failures justify it. — [Using GPT-6: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md)
- Astra tends toward long, heavily formatted answers; it may delegate to subagents less than wanted, so the prompt should say when and how much; it holds coherence over long tasks better than GPT-5.6 Sol and earlier. — [Using GPT-6: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md)
- Reasoning effort for Sol is `low`, `medium` (default), `high`, `xhigh` or `max`; Astra and Sol do not accept `none`. — [Using GPT-6](https://developers.openai.com/api/docs/guides/latest-model)
- The GPT-6 guide does not discuss removing older scaffolding, emphasis, capitals or "MUST" wording. It asks readers to evaluate its suggestions on their own model and workload, and its migration section points to the `openai-docs` skill in the Codex repository, which contains `references/upgrading-to-gpt-6-astra.md` and `references/prompting-guide.md`. — [Using GPT-6](https://developers.openai.com/api/docs/guides/latest-model), [openai-docs SKILL.md](https://raw.githubusercontent.com/openai/codex/main/codex-rs/skills/src/assets/samples/openai-docs/SKILL.md)

**GPT-5.6 Sol prompt guidance (the previous generation; the fullest statement of "less is more")**
- Removing repeated instructions and examples and simplifying tool descriptions can improve task performance; conflicting rules can destabilise behaviour more than missing detail does. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Migration workflow: run representative evals before touching the prompt; remove obsolete scaffolding, repeated instructions and irrelevant tools one group at a time; re-run the same evals after each change; add back only the smallest targeted instruction that fixes a measured regression; do not rewrite a working prompt stack in one go. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Vendor-reported numbers, described as directional and workload-dependent: in internal coding-agent eval runs leaner system prompts raised scores by roughly 10–15%, cut total tokens by 41–66% and cost by 33–67%. No method is given. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Absolute wording (ALWAYS, NEVER, must, only) should be kept for true invariants; judgment calls should be written as decision rules. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Prompts should describe the destination, success criteria and stopping conditions and not prescribe each step. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Repeating ask-first or wait-for-approval instructions produces unnecessary approval requests; blanket brevity instructions can make answers too short. Confirmation should be required for external writes, destructive actions, purchases and material scope expansion. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Verification: give the model tools that can validate its output; for code, run targeted tests, type or lint checks and builds, and if validation cannot run, say why and name the next-best check. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Progress updates: one short update before the first tool call of a multi-step task, sparse updates at phase changes, and no narration of routine tool calls. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)
- Long-running work: define the current layer of work, compact after major milestones, and note that stale persisted reasoning can anchor the model to an outdated approach. — [Prompting guidance for GPT-5.6 Sol](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6)

**Earlier GPT-5.x guides (archived Cookbook recipes; background)**
- GPT-5 guide: contradictory or vague instructions cost more with GPT-5 because the model spends reasoning trying to reconcile them. Cursor found that a maximise-thoroughness context-gathering prompt that suited older models made GPT-5 over-search, and softening it improved tool-use decisions. Eagerness is tuned with `reasoning_effort` plus explicit stop conditions; the model can be used to critique its own prompt. — [GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)
- GPT-5.1 guide: when behaviour is off, check for conflicting instructions; a two-step metaprompt (diagnose with the system prompt plus grouped failure examples, then make a surgical revision) is recommended; user updates of one or two sentences every few tool calls; a plan tool with 2–5 outcome-level items and exactly one in progress; persist to end-to-end completion. — [GPT-5.1 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1_prompting_guide)
- Codex Prompting Guide (for `gpt-5.3-codex`): remove prompting that asks for upfront plans, preambles or status updates during a rollout because it can make the model stop early; default to implementing with reasonable assumptions; use the provided `apply_patch`, `shell` and `update_plan` tools; compaction extends effective context; maximise parallel tool calls. Its recommended starter prompt is itself long and detailed. — [Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)
- Current end-user prompting page: use Goal, Context, Output and Boundaries only as far as they help; start from the result, describe a process only when the process itself matters; boundaries should be the few things that would make a result unusable; ask for a final check on important work; use `/plan` and `/goal` for multi-step work. — [Prompting](https://learn.chatgpt.com/docs/prompting.md)

### Inferences
- The direction of autonomy calibration is model-specific and has reversed: GPT-5.x guides pushed persistence against models that stopped early, while the GPT-6 guide says Astra asks more and needs prompting to proceed. Rule sets written in July 2026 for weaker models, with many "ask the owner first" gates repeated across `AGENTS.md` and four skills, are the configuration OpenAI's GPT-5.6 and GPT-6 guides both associate with unnecessary pauses.
- OpenAI's criterion for absolute language (true invariants only) does not mean deleting hard rules. The program's real invariants (the out-of-sample gate as sole acceptance criterion, no calibration to the negative-control platform, frozen protocols being owner-gated) qualify; procedural preferences stated with the same force do not.
- Taken together, the two guides imply an audit-then-ablate procedure for these skills: list every behaviour-shaping instruction, remove duplicates and stale ones in groups, and re-test after each group.
- The vendor's 10–15% figure is a self-report without a published method; treat it as motivation for testing, not as an expected effect size.

### Gaps
- No GPT-6 Cookbook prompting guide was linked or found, and no GPT-6-specific Codex prompting guide was found. The GPT-6 guide contains no explicit advice on prompt length or emphasis.
- The GPT-5.5 prompt-guidance page could not be opened; third-party blogs attribute to it the advice to begin a migration from a fresh baseline prompt instead of carrying over an older prompt stack, which is unverified here.
- The reference files `upgrading-to-gpt-6-astra.md` and `prompting-guide.md` in the `openai-docs` skill were not read; they may contain the fullest GPT-6 migration procedure.
- No dated release notes for the GPT-6 family were retrieved.

## Key question 3 — The open standards (agents.md, Agent Skills) and the lowest common denominator across Claude and OpenAI agents

### Takeaway
`AGENTS.md` is free-form Markdown with no required structure; the Agent Skills specification fixes only the `SKILL.md` frontmatter (`name`, `description`, four optional fields) and recommends size limits, and deliberately does not say where skills live. The practical incompatibilities are directory locations (Codex reads `.agents/skills`, Claude Code reads `.claude/skills` and by its own docs nothing under `.agents/`), instruction-file precedence (Claude Code ignores `AGENTS.md` when a `CLAUDE.md` is present, by default), and vendor-only extensions.

### Cited Findings
**agents.md**
- `AGENTS.md` is plain Markdown with no required fields or headings; suggested content is a project overview, build and test commands, code style, testing instructions and security considerations. — [agents.md](https://agents.md)
- In nested layouts the file closest to the edited file wins, and explicit user chat prompts override the file. — [agents.md](https://agents.md)
- The format is stewarded by the Agentic AI Foundation under the Linux Foundation, and the site reports use by over 60k open-source projects. — [agents.md](https://agents.md)
- The site lists Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, Junie, Amp, Cursor, RooCode, Gemini CLI, Kilo Code, GitHub Copilot coding agent, Windsurf and others; Claude Code was not in the list as retrieved. Gemini CLI is pointed at the file through `context.fileName` in `.gemini/settings.json`, and Aider through `read: AGENTS.md`. — [agents.md](https://agents.md)

**Claude Code's handling of AGENTS.md**
- Claude Code (v2.1.277 or later) reads `AGENTS.md` natively, but by default only when there is no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` in the working directory or above; when both exist it reads the `CLAUDE.md` files only. A setting (`claude-md-and-agents-md`) loads both, and a `CLAUDE.md` containing an `@AGENTS.md` import includes the shared file without duplication. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Claude Code does not read `AGENTS.override.md`, `AGENTS.local.md`, or anything under a `.agents/` directory. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- A `CLAUDE.md` that only tells Claude in words to go and read `AGENTS.md` works only if Claude chooses to open it; the documented options are the import or a symlink (`ln -s AGENTS.md CLAUDE.md`). Symlink caveats: the Edit and Write tools refuse to write through the link, and on Windows a committed symlink can check out as a one-line text file. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Claude Code treats instruction files as context and not as enforced configuration, targets under 200 lines per `CLAUDE.md`, says contradictory instructions may be resolved arbitrarily, and provides `/doctor prompt-audit`, which checks `CLAUDE.md`, `AGENTS.md`, skills and related files for contradictions, dead references and instructions written for older models. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

**Agent Skills specification**
- Required frontmatter: `name` (1–64 characters; lowercase letters, digits and hyphens; no leading, trailing or consecutive hyphens; must equal the parent directory name) and `description` (1–1024 characters; what the skill does and when to use it). — [Agent Skills specification](https://agentskills.io/specification)
- Optional frontmatter: `license`; `compatibility` (up to 500 characters); `metadata` (string-to-string map); `allowed-tools` (space-separated, marked experimental, support varies by client). — [Agent Skills specification](https://agentskills.io/specification)
- The body has no format restrictions. Recommended limits are under 500 lines and under about 5,000 tokens for `SKILL.md`, with detail moved to `references/`, `scripts/` and `assets/`; file references should be relative to the skill root and one level deep. Catalogue metadata costs about 100 tokens per skill. Validation tool: `skills-ref validate ./my-skill`. — [Agent Skills specification](https://agentskills.io/specification)
- The format was originally developed by Anthropic, released as an open standard, and is open to contributions on GitHub (`agentskills/agentskills`). — [Agent Skills overview](https://agentskills.io/home.md)
- The client showcase lists 46 products by this researcher's count, including Claude Code, Claude, ChatGPT & Codex, Gemini CLI, Cursor, GitHub Copilot, VS Code, OpenCode, OpenHands, Goose, Amp, Junie, Factory, Roo Code and Kiro. — [Client showcase](https://agentskills.io/clients.md)

- The specification does not mandate a location. ### Inferences
- Lowest common denominator for a skill both vendors' agents load identically: a directory whose name equals `name`; frontmatter limited to `name` and `description` (optionally `license` and `metadata`); a quoted description under 1,024 characters that states what and when; a plain-Markdown body under 500 lines and about 5,000 tokens; references one level deep by relative path, each with a stated load condition; scripts invoked by explicit relative path; no Claude-only substitutions or injections and no reliance on `allowed-tools`.
- The repository's four skills already satisfy the frontmatter part. The core skill exceeds the token recommendation (about 6,900 against 5,000) and bundles no references, so none of its content is progressively disclosed; in Claude Code its tail would also fall outside the 5,000-token re-attachment after a compaction.
- The same folders must be reachable at both `.claude/skills/` and `.agents/skills/`. Both vendors document symlinked skill folders, so a symlink is a supported alternative to the present copy; copies need a mechanical equality check, and symlinks carry the Windows and write-through caveats.
- The larger portability hazard in this repository is the entry files. With both `CLAUDE.md` and `AGENTS.md` present, Claude Code by default never loads `AGENTS.md`, so the two digests (31 and 82 lines) are maintained separately and can diverge silently. The documented fix is a `CLAUDE.md` that imports `@AGENTS.md` and adds only Claude-specific lines.
- Vendor differences can be confined to files the other vendor ignores: `agents/openai.yaml` inside each skill folder for Codex, Claude-specific lines in `CLAUDE.md`, and hook configuration in `.codex/` versus `.claude/`.

### Gaps
- Whether Codex tolerates or rejects unknown frontmatter keys was not documented on the pages read; the spec asks clients to be lenient but this was not verified for Codex.
- The final ~7k characters of the Claude Code skills page were not read; the statement that nothing under `.agents/` is read comes from the memory page, in the context of `AGENTS.md`.
- GitHub Copilot and VS Code skill locations were not checked. Gemini CLI's `AGENTS.md` support was taken from agents.md, not from Gemini's own docs.

## Key question 4 — Empirical evidence, 2025–2026, on whether and how instruction files and skills help

### Takeaway
The evidence is thin, mostly preprints, and consistent on three points: always-loaded context files change agent behaviour reliably but do not reliably raise task success and usually raise cost; curated procedural skills help substantially where the model lacks domain procedure and barely at all where it is already competent; and model-generated, exhaustive, or version-mismatched instruction content is neutral to harmful. No study was found that tests emphatic wording or staleness directly.

### Cited Findings
**Context files (AGENTS.md / CLAUDE.md)**
- Gloaguen, Mündler-Sasahara, Müller, Raychev and Vechev, "Evaluating AGENTS.md" (arXiv 2602.11988; v1 12 Feb 2026, v3 29 Sep 2026; poster at the ICLR 2026 workshop "Agentic AI in the Wild"). Design: SWE-bench Lite (300 tasks, 11 Python repositories, LLM-generated context files) and a new benchmark, CTXbench (138 instances from 12 Python repositories with developer-committed context files); agents were Claude Code with Sonnet 4.5, Codex with GPT-5.2 and GPT-5.1 mini, and Qwen Code with Qwen3-30b-coder; conditions were no file, LLM-generated file, developer file; one sample per instance. — [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3), [ICLR 2026 workshop listing](https://iclr.cc/virtual/2026/10021142)
  - LLM-generated files: resolution fell by 0.5 points on SWE-bench and 2 points on CTXbench on average (neither significant: p = 0.87 and 0.37). Developer files: +2.4 points on average (p = 0.21, not significant). Developer versus LLM-generated: about 7 points, p = 0.038, the only significant contrast. — [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3)
  - Per model on CTXbench (none / LLM / developer): Sonnet 4.5 73.2 / 65.2 / 70.3; GPT-5.2 65.2 / 68.1 / 68.1; GPT-5.1 mini 54.3 / 50.7 / 55.8; Qwen3-30b 45.7 / 47.1 / 53.6. — [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3)
  - Cost rose about 20% (SWE-bench) and 23% (CTXbench) with LLM-generated files and up to 19% with developer files; steps rose by roughly 2.5 to 3.9 per task; GPT-5.2 used 14–22% more reasoning tokens. — [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3)
  - Agents did follow the files: a tool named in the file was used about 1.6 times per instance against under 0.01 when unnamed, and agents ran more tests and read more files. The authors conclude the missing benefit is not a failure of instruction-following. — [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3)
  - Repository overviews did not shorten the path to the relevant files. With all other documentation removed, LLM-generated files helped by 2.7% on average, suggesting they are mostly redundant with existing docs. Files generated by stronger models were not better. — [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3)
  - Recommendations: omit LLM-generated context files for now; human-written files should hold only instructions not already available in the repository; evaluate any file before adopting it. Stated limits: Python only, task resolution only, one sample per instance, 138 instances. — [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3)
  - Version caveat: secondary reports of v1 call the benchmark AGENTbench and give a +4% developer-file effect; v3 says CTXbench and +2.4%, and its abstract is worded more mildly. Cite v3. — [search results summarising v1](https://arxiv.org/html/2602.11988v1) (v1 not opened directly)
- Lulla, Mohsenimofidi, Galster, Zhang, Baltes and Treude, "On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" (arXiv 2601.20404, v2 30 Mar 2026, 5 pages). 10 repositories, 124 pull requests, with versus without `AGENTS.md`: median runtime 28.64% lower and output tokens 16.58% lower with the file, completion comparable. Small sample, output tokens only, associational wording. — [arXiv 2601.20404](https://arxiv.org/abs/2601.20404)
- Khatri, "Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories" (arXiv 2607.27250, 28 Jul 2026, single author). Claude Code and Codex, 17 tasks from 3 repositories, 288 runs, gold tests: context strategy did not measurably change correctness for either agent, with equivalence tests bounding any effect at roughly 10–15 points; failures traced to implementation skill, not missing repository knowledge; borderline task difficulty differed by agent (Spearman 0.75), offered as an explanation for conflicting earlier results. Very small task set. — [arXiv 2607.27250](https://arxiv.org/abs/2607.27250)
- McMillan, "Instruction Adherence in Coding Agent Configuration Files: A Factorial Study of Four File-Structure Variables" (arXiv 2605.10039, 11 May 2026, single author). 1,650 Claude Code sessions and 16,050 function-level observations (Sonnet 4.6 primary, Opus 4.6 check); file size, instruction position, file architecture and contradictions in adjacent files produced no detectable effect on compliance with a trivial annotation instruction after correction, with Bayes-factor support for the size and conflict nulls (BF10 0.05–0.10) but not for position or architecture. The largest effect was within-session: about 5.6% lower odds of compliance per additional function generated (OR 0.944), found post hoc and non-monotonic. — [arXiv 2605.10039](https://arxiv.org/abs/2605.10039)
- Chatlatanagulchai et al., "Agent READMEs" (arXiv 2511.12884, v2 9 Aug 2026): 2,303 context files from 1,925 repositories evolve like configuration code through frequent small additions and are hard to read; testing appears in 75.9%, implementation details in 70.8%, architecture in 68.1%, security in 14.8% and performance in 14.5%. Descriptive only. — [arXiv 2511.12884](https://arxiv.org/abs/2511.12884)
- Santos, Costa, Montandon and Valente, "Decoding the Configuration of AI Coding Agents" (arXiv 2511.09268; AGENT 2026 workshop at ICSE): 328 Claude Code configuration files; descriptive, stressing architecture specification. — [arXiv 2511.09268](https://arxiv.org/abs/2511.09268)

**Skills**
- Li et al. (79 authors), "SkillsBench" (arXiv 2602.12670, v4 14 Jun 2026). 87 tasks in 8 domains with deterministic verifiers; 18 model–harness configurations (15 OpenHands, plus Claude Code, Codex and Gemini CLI); 3 trials per cell. — [arXiv 2602.12670v4](https://arxiv.org/html/2602.12670v4)
  - Curated skills raised the mean pass rate from 33.9% to 50.5% (+16.6 points); every configuration improved, from +4.1 to +25.7 points. Codex with GPT-5.5 reached 66.5% with skills and Claude Code with Opus 4.7 reached 61.2%. — [arXiv 2602.12670v4](https://arxiv.org/html/2602.12670v4)
  - Gains by domain ran from +28.8 points (natural science, 14 tasks) to +11.6 (software engineering, 16 tasks) and +9.7 (mathematics and operations research, 8 tasks). Skills hurt on 13 of 87 tasks (worst −7.4 points). — [arXiv 2602.12670v4](https://arxiv.org/html/2602.12670v4)
  - Quantity and length: one skill +18.0, two or three +19.0, four or more +10.1. Compact +19.0, standard +21.5, detailed +14.5, comprehensive +0.7. — [arXiv 2602.12670v4](https://arxiv.org/html/2602.12670v4)
  - Skills the agent wrote for itself scored below the no-skill baseline on all three configurations tested (−8.1 Claude Code with Opus 4.7, −11.3 Codex with GPT-5.5, −11.5 Gemini CLI with Gemini 3.1 Pro), against +18.2 to +24.8 for curated skills on the same configurations. — [arXiv 2602.12670v4](https://arxiv.org/html/2602.12670v4)
  - Author-stated limits: no length-matched control, so some of the gain may come simply from added context length; curated skills are far above typical ecosystem quality; terminal, containerised tasks only; skill-composition effects unstudied. — [arXiv 2602.12670v4](https://arxiv.org/html/2602.12670v4)
- Han et al., "SWE-Skills-Bench" (arXiv 2603.15401, 16 Mar 2026). 49 public software-engineering skills, about 565 task instances, Claude Code with Haiku 4.5 only. 39 of 49 skills changed nothing; the mean gain was +1.2 points (89.8% to 91.0%); 7 skills helped (+7.1 to +30.0); 3 hurt (to −10.0), attributed to version-mismatched guidance and to surplus template content being copied rigidly. Token overhead among the no-effect skills ranged from −78% to +451%. Twenty-four skills sat at a 100% ceiling in both conditions. One model, one harness, preprint. — [arXiv 2603.15401](https://arxiv.org/html/2603.15401v1)
- Vercel engineering blog (Gao, 27 Jan 2026; industry report, not peer reviewed). On Next.js 16 API tasks absent from training data: baseline 53%; a skill with default behaviour 53%, with the skill never invoked in 56% of cases; a skill plus explicit instructions 79%; an 8 KB compressed documentation index placed in `AGENTS.md` 100%. A forceful invoke-the-skill-first instruction did worse than an explore-the-project-first instruction. Agent, model and sample size are not stated. — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)

**Instruction load**
- Jaroslawicz, Whiting, Shah and Maamari, "How Many Instructions Can LLMs Follow at Once?" (IFScale, arXiv 2507.11538, Jul 2025): with up to 500 keyword-inclusion instructions, the best of 20 frontier models reached 68% at maximum density, with a bias toward earlier instructions. One synthetic task type; mid-2025 models. — [arXiv 2507.11538](https://arxiv.org/abs/2507.11538)

**Where findings conflict or are weak**
- Efficiency: Lulla et al. report lower runtime and output tokens with `AGENTS.md`; Gloaguen et al. report more steps and about 20% higher cost. The designs, measures and file sources differ, and neither is large. — [arXiv 2601.20404](https://arxiv.org/abs/2601.20404); contradicted by [arXiv 2602.11988v3](https://arxiv.org/html/2602.11988v3)
- Skills: +16.6 points on SkillsBench against +1.2 on SWE-Skills-Bench. The second ran one small model on software tasks where the base pass rate was already about 90%. — [arXiv 2602.12670v4](https://arxiv.org/html/2602.12670v4); contrasted with [arXiv 2603.15401](https://arxiv.org/html/2603.15401v1)
- Contradictions: McMillan finds no effect of contradictory adjacent files on a trivial instruction; OpenAI's and Anthropic's documentation both assert that conflicts degrade or randomise behaviour, without published data. — [arXiv 2605.10039](https://arxiv.org/abs/2605.10039); [GPT-5.6 guidance](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6); [Claude Code memory docs](https://code.claude.com/docs/en/memory)

### Inferences
- Extra instructions hurt through three measured routes: cost and exploration overhead with no success gain (Gloaguen); irrelevant or exhaustive content that agents follow or copy anyway (SkillsBench "comprehensive" at +0.7; SWE-Skills-Bench template copying); and content that is wrong for the current state of the project (SWE-Skills-Bench version mismatch). The second and third describe a long core skill that carries point-in-time project state.
- The benefit of a skill tracks the gap between what the task needs and what the model already knows. A bespoke research method with frozen specifications and unusual pitfalls is far from training data, so the SkillsBench natural-science result is the more relevant analogue than the software-engineering nulls. That supports keeping the method contract, not deleting it.
- In Gloaguen's per-model table the weakest model gained most from developer files and the strongest Claude model lost slightly. This fits the owner's premise that files written for weaker models need redesign for stronger ones, but it rests on single samples and non-significant differences.
- Models writing their own skills did badly in SkillsBench, and LLM-generated context files did worse than human ones. A redesign should therefore be human-specified and grounded in the project's actual records, with model drafting followed by measured testing, and not a wholesale model rewrite.
- McMillan's within-session decay suggests that requirements which must hold at the end of a long session are better enforced at commit time by tests and hooks than by instruction salience.
- The only data bearing on emphatic wording is Vercel's anecdote; the case against capitals and stacked absolutes rests on vendor guidance, not on controlled evidence.

### Gaps
- No controlled study of emphatic language (capitals, MUST/NEVER density) on current agents was found.
- No study measuring the effect of stale or outdated context-file content over time was found; the nearest evidence is the version-mismatch harm in SWE-Skills-Bench.
- No study uses GPT-6-generation or Claude Opus 5.x / Fable models; the newest models tested are GPT-5.5 and Opus 4.7/4.8 (SkillsBench).
- No study covers long-horizon scientific or research workflows; every benchmark is a bounded task with a deterministic checker.
- Apart from two workshop papers, the sources are unreviewed preprints, three of them single-author.

## Key question 5 — Different vendors' models working in one repository

### Takeaway
Authoritative guidance is sparse and practical: share one instruction source, keep concurrent writers in separate worktrees, and treat cross-model review as a supported workflow. The limited evidence says a second, different model finds partly different errors, but that the gain is not cleanly separable from reviewer capability and that strong models' errors are substantially correlated, so cross-model review is not independent verification.

### Cited Findings
- OpenAI publishes a Claude Code plugin, `codex-plugin-cc`, that calls the local Codex from inside Claude Code: `/codex:review` (read-only review of current changes or a branch diff), `/codex:adversarial-review` (steerable challenge of design choices; does not fix code), `/codex:rescue` (delegate investigation or a fix), plus status, result, cancel and setup commands. An optional stop-time review gate blocks Claude from finishing until Codex's findings are addressed; the README warns it can create a long Claude–Codex loop and drain usage limits. The README gives no stated rationale for cross-model review. — [openai/codex-plugin-cc](https://github.com/openai/codex-plugin-cc)
- Codex documentation advises against two chats changing the same files or writing to the same connected source, recommends Git worktrees for parallel coding chats, and warns that simultaneously editing agents can conflict. — [Long-running work](https://learn.chatgpt.com/docs/long-running-work.md), [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md), [Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- The Codex prompting page says to tell Codex when you have reverted or edited its changes so that it does not overwrite your edit. — [Prompting](https://learn.chatgpt.com/docs/prompting.md)
- Claude Code's `/doctor prompt-audit` covers `AGENTS.md` and skills as well as `CLAUDE.md`, and OpenAI's GPT-6 guide recommends auditing the same files; both vendors therefore provide or recommend an audit of the shared instruction surface. — [Claude Code memory docs](https://code.claude.com/docs/en/memory), [Using GPT-6: GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md)
- Song, "When Does a Second Model Help? Cross-Model Review in LLM Verification" (arXiv 2610.01471, v2 6 Oct 2026, single author). 30 artifacts with 150 planted errors, 10 conditions, 900 review sessions, three reviewer models from two developers. A top-tier cross-model reviewer did not differ significantly in F1 from a same-model reviewer in a fresh session; the two found partly different errors (Jaccard overlap 41.2%); one same-model plus one cross-model review caught 56.7% of planted errors against 42.7% for two same-model reviews (Holm-adjusted p = 0.006), but not significantly more than two reviews by the stronger cross-model reviewer, so model difference and reviewer capability are confounded; a lightweight cross-model reviewer did no better than same-model review. Data available on request only. — [arXiv 2610.01471](https://arxiv.org/abs/2610.01471)
- A secondary summary of the same paper reports a split by artifact type (same-model ahead on code, cross-model well ahead on documents); this was not visible on the arXiv abstract page and is unverified. — [agentpatterns.ai summary](https://agentpatterns.ai/verification/cross-model-review-independence/)
- Kim, Garg, Peng and Garg, "Correlated Errors in Large Language Models" (arXiv 2506.07962, ICML 2025): across more than 350 models, two models that were both wrong gave the same wrong answer 60% of the time on one leaderboard dataset; shared provider or architecture raised correlation; larger, more accurate models were highly correlated even across providers. — [arXiv 2506.07962](https://arxiv.org/abs/2506.07962)
- Panickssery, Bowman and Feng, "LLM Evaluators Recognize and Favor Their Own Generations" (arXiv 2404.13076, Apr 2024): evaluator models can recognise their own outputs, and self-preference strength rises linearly with self-recognition. — [arXiv 2404.13076](https://arxiv.org/abs/2404.13076)

### Inferences
- A fresh-context reviewer matters at least as much as a different-vendor reviewer; the cheapest robust arrangement in the Song data is one fresh same-model review plus one top-tier cross-model review.
- Because strong models share errors, agreement between a Claude model and a GPT-6 model is weak evidence of correctness. For this program the independent check has to be mechanical: the out-of-sample gate, the legacy guard and the test suite. Cross-model review is a supplement for finding issues, not an acceptance criterion.
- Self-preference is an argument for having the other vendor's model, or a blinded comparison, judge whether a redesigned skill is better than the old one.
- Concurrent sessions need separation at the filesystem level (one worktree per live agent) plus an agreed convention for shared append-only records; instructions alone do not prevent write collisions. This project's memory notes record a concurrent Codex session overwriting a Claude draft at the same path, which is this failure.

### Gaps
- No vendor document was found that addresses two vendors' agents working concurrently in one working tree, and no empirical study of write collisions or coordination among heterogeneous coding agents was found.
- No study tests cross-model review of scientific or statistical work products.
- The Song paper's reviewer models are not named on the abstract page; the full text was not read.

## Implications for redesigning the rank-diffusion skills

This section is inference from the findings above plus the local measurements in the header. The skills encode the program's method contract, so any change is owner-gated.

1. **Fix the entry-file split first (portability; highest leverage, lowest risk).** With both `CLAUDE.md` and `AGENTS.md` present, Claude Code reads only `CLAUDE.md` and Codex reads only `AGENTS.md`, so the two agents start from different digests. Make `AGENTS.md` the single always-loaded contract and reduce `CLAUDE.md` to an `@AGENTS.md` import plus Claude-only lines (documented by Anthropic). Keep `AGENTS.md` far below Codex's 32 KiB cap and within Claude's 200-line target; it is 82 lines now.

2. **What must be identical for both vendors, and what may differ.**
   - Identical: every `SKILL.md` and every bundled reference or script; the always-on contract in `AGENTS.md`. Frontmatter stays at `name` and `description` only, descriptions quoted and under 1,024 characters, no Claude-only substitutions or injections, references one level deep by relative path.
   - May differ: Claude-only lines in `CLAUDE.md`; a Codex-only `agents/openai.yaml` sidecar per skill (for example `policy.allow_implicit_invocation`); hook and rule configuration under `.claude/` and `.codex/`; one or two calibration lines per vendor (for Astra, per OpenAI: proceed on reversible work, stop only at the named owner gates, and user instructions outrank skill text).
   - Mirror mechanics: keep `.claude/skills` and `.agents/skills` in lockstep either by a symlink (supported by both vendors; mind Windows checkouts and Claude's refusal to edit through links) or by keeping copies and adding a test that fails when they differ. A convention stated only in prose is the weakest option.

3. **Move content between `AGENTS.md` and skills by one test: must it hold in every session?**
   - `AGENTS.md`: the handful of true invariants (sole acceptance criterion, protected committed results and the guard that proves it, platform data rules, owner-gated items), where the canonical record is, the exact verification commands, and a routing table saying which skill to load for which kind of work.
   - Skills: procedures. Replace the instruction to read the core skill in full before every session with routing in `AGENTS.md` and descriptions that say what and when; drop authorship and date text from descriptions, since it consumes catalogue budget without helping triggering.

4. **Rule language.** Keep absolute wording for the true invariants and say why each exists; rewrite the rest as decision rules or defaults with a reason (OpenAI GPT-5.6 guidance; agentskills.io best practices). State each rule once: the same prohibitions currently recur across `CLAUDE.md`, `AGENTS.md` and the skills, and both the GPT-5.6 and GPT-6 guides tie repeated ask-first rules and conflicting skill text to needless pauses. Add one explicit precedence line (owner's instruction in chat, then `AGENTS.md` invariants, then skill procedure). Run Claude Code's `/doctor prompt-audit` and the GPT-6 guide's audit over the same files and reconcile the two reports.

5. **Length and structure.** Split the core skill (about 6,900 tokens, nothing progressively disclosed) into a `SKILL.md` under about 5,000 tokens that holds the method and the gotchas an agent would otherwise get wrong, plus `references/` files (pitfall catalogue, frozen-spec details, metric hierarchy) each with a stated load condition. SkillsBench's ordering (standard and compact well ahead of comprehensive) and Claude Code's 5,000-token post-compaction re-attachment both point the same way. Cut anything a top-tier model does correctly without being told, but only after testing shows it is redundant. Do not have a model regenerate the skills from scratch: self-generated skills and LLM-generated context files both underperformed in the studies above.

6. **Volatile state.** Take point-in-time project state (current agenda, latest numbers, dated findings) out of the skills and point to the dated sections of `MODEL_STATUS.md`, which the repository already designates as canonical. Stale guidance is the one mechanism with measured harm (version-mismatched skills), and OpenAI warns that stale persisted context anchors a model to an outdated approach. The core skill's ten dated entries and its agenda section predate the October re-entry, when two agendas were proposed and neither adopted.

7. **Verify that the redesign changes behaviour for the better, before adopting it.**
   - Write the predictions down first, as the program does for model changes: a small fixed set of realistic session prompts per skill (fit and evaluate a variant; take in a new panel; record a session; supersede a result; a tempting spec-fishing opportunity; a request touching a frozen threshold), each with observable assertions (ran the legacy guard and the test suite; reported the multi-split gate and not a single split; appended a dated section and did not rewrite history; stopped at an owner gate; did not stop elsewhere).
   - Run old skills against new skills in clean contexts, on both Claude Code and Codex, at least three runs per cell, and record pass rates, tokens, wall time and counts of clarification pauses (agentskills.io evaluation guide; SkillsBench used three trials). Read the transcripts, not only the outcomes.
   - Test triggering separately: about 20 should-trigger and near-miss should-not-trigger prompts per skill, three runs each, with a held-out validation subset (agentskills.io description guide). Vercel's 56% never-invoked result shows a skill can fail silently at this step.
   - Change one group of instructions at a time and re-run; restore only the smallest instruction that repairs a measured regression (OpenAI GPT-5.6 migration workflow). When Astra pauses, ask it to name the `SKILL.md` line responsible.
   - Confirm what each agent actually loaded: Codex's instruction-summary command and logs, Claude Code's `/memory`.
   - Have the comparison judged blind, or by the other vendor's model, and keep the mechanical gates as the acceptance criterion; cross-model agreement is not independent evidence.
   - Put end-of-session requirements (guard, tests, mirror equality) into hooks or CI on both sides, since adherence decays within long sessions and both vendors describe instruction files as guidance, not enforcement.
   - Expect small, noisy effects. The published studies mostly could not distinguish context-file effects from zero with 100 to 300 tasks, so a handful of scenarios supports only coarse conclusions: no regression on the invariants, fewer needless pauses, lower token cost.
